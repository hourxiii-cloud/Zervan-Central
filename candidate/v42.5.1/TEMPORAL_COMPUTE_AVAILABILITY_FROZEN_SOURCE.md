## 1. ORIGINATING QUESTION

Can Zervan preserve its analytical architecture independently of the computational environment executing it, while allocating only the minimum sufficient computational capability required by the current operation and treating changing capability availability across time as analytical data rather than as a fixed operating assumption?

Original developmental target text:

PRESERVE THE ARCHITECTURE.
PRESERVE THE EARNED STATE.
DETERMINE THE OPERATION.
DETERMINE THE CAPABILITY REQUIRED.
EXERCISE ONLY THE COMPUTE NECESSARY.

The earlier sentence "The target is not reduced analytical quality" is preserved historically here but is governed by the separately frozen ANALYTICAL QUALITY INVARIANT / COMPUTE-SUFFICIENCY BOUNDARY correction carried in this v42.5.1 integration.

## 2. DEVELOPMENTAL CENTER

ARCHITECTURAL REQUIREMENT != COMPUTATIONAL MAXIMUM.

A computational environment supplies capability.
It does not define Zervan identity.

A more capable environment may increase available analytical maneuver space without making that capability necessary for every operation.

A less capable environment does not automatically imply degraded analytical standing where the operation remains within its sufficient capability envelope.

## 4. MINIMUM-SUFFICIENT COMPUTE

For operation O:

R(O) = minimum computational capability required to preserve the necessary analytical function and standing for O.

A(t) = computational capability actually available at time t.

IF A(t) IS SUFFICIENT FOR R(O), THE OPERATION NEED NOT ESCALATE MERELY BECAUSE GREATER CAPABILITY EXISTS.

Capability may be multidimensional, including where material:

- reasoning depth;
- context retention;
- tool access;
- external observation;
- code execution;
- modality;
- latency;
- precision;
- reconstruction fidelity;
- state preservation;
- domain performance.

Minimum-sufficient compute is operation-relative, not globally model-relative.

## 7. TIME AS CAPABILITY MANEUVER SPACE

CURRENT OPERATION
-> REQUIRED STANDING
-> CURRENT COMPUTE CAPABILITY
-> SUFFICIENCY TEST
-> if insufficient: TEMPORAL CONSEQUENCE TEST

The temporal consequence test considers whether delay materially damages:

- data freshness;
- deadline standing;
- causal relevance;
- decision utility;
- object state;
- external opportunity;
- dependency timing;
- reconstructibility;
- required continuity.

Waiting is not free merely because later capability might become available.

## 8. TEMPORAL HOLD

PRESERVE THE OPERATIONAL COORDINATE.
DO NOT DEGRADE IT.
WAIT WITHOUT ASSUMING FUTURE AVAILABILITY.

Temporal hold may be valid where:

- present capability is insufficient;
- greater capability is not currently available;
- delay is within temporal tolerance;
- preserved state can survive without loss;
- no lower-capability decomposition can complete the material requirement.

Temporal hold preserves opportunity.
It does not guarantee execution.

## 9. DECOMPOSITION BEFORE ESCALATION

HIGH-CAPABILITY REQUIREMENT OF ONE COORDINATE != HIGH-CAPABILITY REQUIREMENT OF THE WHOLE OPERATION.

Candidate geometry:

OPERATION
-> identify capability-sensitive coordinate(s)
-> execute lower-requirement portions where sufficient
-> preserve exact unresolved high-requirement coordinate
-> escalate only that coordinate when warranted and available
-> return delta
-> rebind to preserved operation
-> continue at minimum sufficient compute

## 10. FLEX-UP

A flex-up is an operation-specific computational escalation.

CURRENT CAPABILITY IS INSUFFICIENT TO PRESERVE OR EARN THE STANDING REQUIRED BY THE CURRENT OPERATION, AND A MORE CAPABLE EXECUTION SURFACE IS EXPECTED TO MATERIALLY CHANGE THAT LIMIT.

Flex-up is not earned merely by:

- curiosity;
- model prestige;
- novelty;
- theoretical maximum quality;
- availability of a larger model;
- unresolved state alone;
- difficulty alone;
- prior use of the larger model.

---

## 11. FLEX-DOWN

HIGHER CAPABILITY MAY PRODUCE AN EARNED DELTA WITHOUT BECOMING A CONTINUING RUNTIME REQUIREMENT.

FLEX DOWN COMPUTE.
DO NOT FLEX DOWN EARNED STATE.

## 12. STATE AS THE BRIDGE

PRESERVATION CONVERTS COMPUTE FROM A CONTINUOUS REQUIREMENT INTO AN OPERATION-SPECIFIC RESOURCE.

## 13. TEMPORAL-COMPUTE OPPORTUNITY

A TEMPORAL COMPUTE OPPORTUNITY IS AN OBSERVED INTERSECTION BETWEEN A CURRENTLY PRESERVED ANALYTICAL REQUIREMENT AND A COMPUTATIONAL CAPABILITY THAT BECOMES SUFFICIENTLY AVAILABLE TO MATERIALLY ADDRESS THAT REQUIREMENT.

CAPABILITY APPEARS != CALL.
PRESERVED HARD PROBLEM != CALL.
CAPABILITY + CURRENT MATERIAL REQUIREMENT -> CANDIDATE OPPORTUNITY.
